# Aggregation Engine и Match Data Store v1

[Решение владельца в Issue #91](https://github.com/Dmitry312/tennis-predictor/issues/91)
разделяет обработку завершённого матча и расчёт истории по запросу.

| Путь | Выполняемая работа |
| --- | --- |
| Завершение или исправление матча | Проверить версию канонических данных, рассчитать наблюдаемые факты и сохранить две стороны со счётчиками. |
| Запрос истории игрока | Прочитать пригодные наблюдения по проверенному ID и дате с явной политикой доступности. Будущий Feature Engine сможет рассчитать из них только запрошенные признаки. |
| Feature Store | Будущее хранилище прематчевых векторов по запросам Feature Engine. |

После завершения матча сохраняются факты матча и сетов. Расчёт Elo, формы,
усталости, состояния игрока и будущих векторов относится к будущему Feature Engine.
Одинаковый код этого движка должен использоваться для предсказания и сборки датасетов.

## Запуск и файлы

```bash
uv run --locked python scripts/build_match_data.py
```

Команда автоматически собирает либо переиспользует проверенный канонический снимок,
берёт один матч за раз и публикует снимок в `data/ml/match-data/<mode>/versions/<id>`.
`CURRENT` переключается атомарно после готовности файлов. В снимке находятся
`manifest.json`, `quality_report.json`, читабельный `matches.txt` с отчётом по
каждой стороне и шарды `match_sides.parquet` и `metrics.parquet` по матчам.
Идентификатор включает точный канонический снимок, хеши шардов, индекс и отчёты.
Неизменившийся вход переиспользует байты через SQLite, а текущая публикация
содержит только ревизии заявленного канонического снимка. Счётчики запуска и
инвалидации возвращаются отдельно. Исправление, удаление и новая запись сообщают
затронутые матчи, проверенные ID и самую раннюю дату.

Канонический вход и Parquet проверяются по хешам. При ошибке активный снимок
сохраняется. Уже проверенные ревизии могут остаться в кэше для безопасного повтора.
Снимок воспроизводим в пределах одной версии кода и среды сериализации. Clock
используется только в отдельном журнале live-активаций.

## Факты и формулы

Зерно наблюдения включает матч, сторону, метрику, scope (0 — матч, 1+ — сет),
при необходимости гейм, версию и исходную строку. Один ключ может иметь несколько
наблюдений при конфликте. В строке сохраняются числитель, знаменатель, размер
наблюдаемой выборки, качество и покрытие, исходное значение и ссылки с хешами и
временами доказательств. `MISSING` означает отсутствие, `PARTIAL` — неполноту,
`CONFLICT` — расхождение, `UNVERIFIED` — непроверенную семантику или связь,
`VALID` — успешно проверенное наблюдение. При нескольких версиях одной семьи
факты видны по отдельности, а история не выбирает версию автоматически.
Ограничения одной семьи оставляют независимые факты других семей доступными.

| Семья | Формула и источник |
| --- | --- |
| Победа, выигранные и проигранные сеты, разница | Победитель из канонического завершённого результата. Подсчёт выигранных и проигранных сетов, разница = выигранные минус проигранные. |
| Геймы и разница | Сумма игр своей и противоположной сторон из завершённых валидных сетов. Очки матчевого тай-брейка хранятся в счёте и исключены из геймовых сумм. |
| Длительность | Исходная строка из канонического результата. Единица и аддитивность формата пока не подтверждены. |
| Подача | Исходные `first/second_serve_points_won` и `first/second_serve_points_all`; доля = won / all. Эйсы и двойные ошибки хранятся отдельно. |
| Сервисные геймы и брейк-пойнты | `service_games_won / service_games_all`, `break_points_won / break_points_all` по текущему контракту маппинга. Сохранённые брейк-пойнты требуют самостоятельного доказательства. |
| Приём | `(оппонент.all − оппонент.won) / оппонент.all` для первой или второй подачи. Один матч, scope, источник и ревизия статистики. Уникальная связка с деталями по receipt и нормализованные алиасы обеих сторон подтверждают порядок. |
| Winners, unforced errors и серии | Отдельные исходные счётчики. Непроверенная семантика исключает их из истории. Максимумы серий не складываются. |
| PBP | Число однозначно наблюдаемых выигранных очков на сторону и гейм. Выборка — число наблюдаемых очков с известным победителем. Полнота отдельно, только из проверенного флага и непрерывной последовательности. Пропущенные розыгрыши остаются пропущенными. |

Состав 14 счётчиков следует из `STAT_FIELDS`. Канонические проверки
проверяют пределы won/all и согласованность полных наборов сетов с матчем.
Сырые счётчики разных scope сохраняются, а потребитель выбирает одну базу
агрегации. Объединение долей — `sum(won) / sum(all)` с одним наблюдением
на матч и одинаковым scope. Неизвестные и нулевые знаменатели не дают долю.
Коэффициенты и рейтинги не входят в слой фактов для модели.

На реальном каталоге 368682 даёт 12 выигранных геймов у первой стороны.
Там же есть пригодные счётчики подачи и приёма при неполной PBP. Исходное
значение длительности первого сета `00:34` сохранено. Снятия и walkover
сохраняются со статусом. При отсутствующем счёте нет метки или нулевой
замены.

## Чтение истории и будущий live hook

`SnapshotReader.match(match_id)` отдаёт все наблюдения одной ревизии.
`SnapshotReader.history(player_id, prediction_date=...)` использует индекс
проверенного ID и только даты строго до даты матча прогноза (UTC).
Это согласованное историческое допущение о последующей доступности
валидированных фактов. Поле `available_at` при этом сохраняет доказанное
время или NULL. Аргумент `observed_cutoff` включает строгую проверку времени
доступности факта и доказательства идентичности. Неизвестные или запоздавшие
доказательства закрывают этот путь. История не строится по строкам имён или
предварительным ID.

`unique_target_day(player_id, date)` — проверка для будущего dataset builder.
Он должен применить её к обоим проверенным участникам целевого матча.
Дни с несколькими записями одного игрока исключаются из обучающих и
оценочных целей. Факты этого дня остаются доступны со следующей даты.
Сам dataset builder остаётся отдельной задачей.

Будущий коллектор после успешной записи завершённого матча или исправления
должен нормализовать один канонический `MatchInput` с устойчивым
`input_revision` и вызвать `MatchDataStore.process(match, live=True)`.
Для исправления передать `expected_previous=<active revision>`.
Первая обработка, повтор и исправление сохраняются атомарно в одной
транзакции с индексом. После ошибки предыдущая активация сохраняется.
Повтор активной ревизии сохраняет прежнее время успешной обработки.
`MatchDataStore.history(player_id, prediction_date=..., as_of=...)` выбирает
только успешно обработанную ревизию, допустимую на момент запроса.
Параллельная работа с реестром должна поставлять подтверждённые ID и
времена решений через канонический вход. Слой агрегации не меняет реестр.

## Вопросы владельцу и границы

1. Какова единица длительности `duration`, и можно ли складывать её по сетам
   при задержках или незавершённой игре?
2. Подтверждены ли семантика `break_points_won/all` и возможность вывести
   saved у оппонента? Какие случаи создают неполный знаменатель?
3. Совпадают ли определения winners, unforced errors и максимумов серий
   между источниками? Как учитывать пересечение границ сетов?
4. Какой источник доказывает конечный розыгрыш и полноту PBP? Как связывать
   PBP и статистику разных ревизий при расхождениях?
5. Покрывает ли связь сторон NBBet также статистику у записей без
   подтверждённых алиасов, или требуется отдельное доказательство?

Для исторического развёртывания понадобится контролируемая стадия импорта.
В v1 байты хранятся в SQLite и в опубликованных Parquet-шардах, а число
записей манифеста и индекса пропорционально каталогу. Повтор проверяет файлы
и формирует отчёт, сохраняя расчёт фактов неизменившихся матчей. Перед
масштабированием нужны партиционирование индекса и политика хранения старых
снимков. Исходные версии каталога должны оставаться доступны для аудита.
