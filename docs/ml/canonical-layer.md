# Canonical Data Layer v1

## Запуск

В окружении с зависимостями из `uv.lock` выполните из корня репозитория:

```bash
uv run --locked python scripts/build_canonical_layer.py
```

По умолчанию обрабатывается `docs/ml/data_catalog/index.json` с настройками
`docs/ml/canonical_layer_v1.json`. Результат сохраняется в
`data/ml/canonical/strict_as_of/versions/<version>/`. Скрипт выводит сводку,
а `--json` выводит отчёт текущего запуска с разбивкой проверок по
источникам и категориям, изменениями входов и датами инвалидации.
В каждой версии лежат сводка качества `quality_report.json`, манифест
артефактов `manifest.json` и 11 таблиц Parquet. В JSON-файле `CURRENT`
хранятся `version` последнего опубликованного локального снимка режима
и `published_at` — UTC-время переключения указателя. Повторный запуск
без изменений сохраняет указатель и его время.
Флаги `--catalog`, `--output`, `--config`, `--mode` и `--prediction-cutoff`
предназначены для отдельных сценариев.

## Компоненты и физические схемы

Адаптер сверяет контрольные суммы каталога, манифестов и файлов. Каждая порция
данных соответствует одному матчу и содержит все перечисленные версии источников.
Преобразование использует реестр игроков и правила счёта проекта. Независимые
проверки формируют строки качества перед записью. Локальное хранилище пишет Parquet
по матчам и потоково собирает файлы снимка. Новому адаптеру достаточно предоставлять
индекс, проверять байты и выдавать версионированные `Bundle`; преобразование и
политика качества работают поверх этого формата.

Физические схемы и nullability заданы в
[`contracts.py`](../../src/tennis_predictor/ml/canonical_layer/contracts.py).
Идентификаторы UUID записываются каноническим текстом. Счётчики и порядковые
номера имеют тип int64, дата матча — date32, время — UTC с точностью до
микросекунд, коэффициенты — decimal128(7,3). `NULL` означает отсутствие
доказанного значения. Исходные значения сохраняются в разрешённых полях
и через ссылки на неизменяемые файлы каталога.

Все таблицы содержат `manifest_id`, `source_version`, `content_sha256`,
`evidence_ref`, `evidence_status`, `transform_version` и поля времени.
`manifest_id` указывает на наблюдение источника в `data_manifest`.
`content_sha256` хеширует каноническое представление строки или проверенный
файл экспорта для записи уровня источника. `evidence_ref` указывает на
файл и исходный индекс строки либо на решение рецензента. Манифест сохраняет
ключ объекта, идентификатор версии, ETag, время изменения, хеш объекта и схемы
при наличии этих данных.

| Таблица | Зерно и содержимое |
| --- | --- |
| `players` | Наблюдение игрока в конкретном матче, ключ `(manifest_id, player_id)`. Статус, исходное имя и версия реестра. |
| `player_aliases` | Алиас стороны, ключ `(manifest_id, alias_id)`. Исходное и нормализованное имя и происхождение связи. |
| `tournaments` | Проверенный контекст издания, ключ `(manifest_id, edition_id)`. Формат и правило решающего сета. |
| `matches` | Строка каталога, ключ `match_id` в снимке. Стороны, дата, контекст и исходная ссылка на дубликат. `duplicate_of` может указывать за пределы снимка. |
| `match_results` | Результат на исходную строку, ключ `(source_version, match_id, evidence_ref)`. Упорядоченные структуры с геймами, тай-брейком и исходной длительностью. Сторона источника, победитель конкретного матча и допущенная целевая метка хранятся раздельно. |
| `match_player_stats` | Сторона источника и scope на версию. `scope=0` обозначает матч, положительный scope — номер сета. При конфликте полный ключ включает `evidence_ref`. |
| `match_player_pbp` | Каждая исходная строка, ключ `(source_version, match_id, evidence_ref)`. Ожидаемый ключ последовательности — версия, матч, сет, гейм и очко. |
| `player_rankings` | Ранг на сторону исходной строки. Ключ `(source_version, match_id, evidence_ref, player_side)`. Дата действия рейтинга и связь с игроком допускают NULL. |
| `match_odds` | Одна наблюдаемая пара на версию строки матча. Время захвата, статус источника и запрет использования в модели. |
| `data_quality` | `quality_id` хеширует контекст матча, версию, ссылку, категорию, правило и причину. |
| `data_manifest` | Одно наблюдение версии исходного файла или объекта, ключ `manifest_id`. Охват, число строк, происхождение и доступные контрольные суммы. |

Уточнения к [предложенным контрактам](data_audit/canonical_contracts.md):
ключи конфликтующих исходных строк включают точную ссылку, чтобы хранить
расхождения без выбора произвольной записи. Для рейтинга достаточно
наблюдаемого ранга и стороны. Турнирная строка требует проверенного издания.
Доступный источник кандидата и принадлежность стороны матчу имеют разные
доказательства. Покрытие, качество и достоверность источника имеют собственные
поля. Статусы качества — `valid`, `missing`, `partial`, `conflict`,
`unverified`. Последний включает неизвестную совместимость версий.

## Правила качества и доказательства

- **Игроки.** Существующие правила нормализации и журнал `PlayerRegistry`
  применяются в пределах наблюдения матча. Без проверенной связи ID привязан к
  матчу и стороне. Повторение имени в другом матче создаёт отдельное наблюдение.
  Совпадение нормализованных имён обеих сторон или совпадение их проверенных
  ID переводит связь в карантин. Проверенное решение может ссылаться на один
  устойчивый идентификатор в разных матчах. Для строгого среза время записи
  такого решения должно предшествовать cutoff.
- **Результат.** По [согласованному контракту NBBet](https://github.com/Dmitry312/tennis-predictor/pull/90#issuecomment-7195523871)
  при совпадающем NBBet ID `score_team1` относится к `matches.player1`,
  а `score_team2` — к `matches.player2`. Для статуса 3 проверяются
  последовательность и законность сетов. Итог 2:0 или 2:1 устанавливает
  победителя в BO3, итог 3:0, 3:1 или 3:2 — в BO5. `best_of` в строке
  результата может следовать из счёта. Проверенное правило турнира, если
  оно есть, ограничивает допустимый формат. Без него проверяются обычные
  сеты и стандартные тай-брейки, а `decider_rule` остаётся NULL.
  Неоднозначные форматы передаются владельцу на подтверждение.
  `winner_side` описывает победителя конкретного матча. Он доступен
  при корректном счёте и отсутствии противоречий в совместимых
  источниках, в том числе при пропуске `players_json`, глобальных
  ID игроков, проверенного издания и независимого источника.
  `target_p1_win` принимает 1 или 0 для каждого подтверждённого
  победителя матча. `target_eligible`, `player_state_eligible` и
  `model_baseline_label` сохраняют отдельные требования к версии,
  идентичности, доступности и cutoff. `exclusion_reason` объясняет
  отсутствие победителя или ограничение допуска.
  Результаты с незавершённым статусом и пропуски счёта учитываются
  отдельно.
- **Статистика.** Все 14 метрик разворачиваются по сторонам. Сохраняются
  исходные значения, числители и знаменатели. Проверяются счётчики, отношения
  won/all, дубликаты scope и сумма аддитивных метрик по совместимому полному
  набору сетов. Максимумы серий хранятся с отдельным ограничением семантики.
  Приём проверяется через счётчики подачи противоположной стороны того же
  scope. Проверки отдельных метрик, подачи, приёма и брейков независимы.
- **PBP.** Хранятся все наблюдённые розыгрыши с исходными именами полей
  внутри `raw_json`, ограниченного строкой розыгрыша. Проверяются порядковые
  ключи, дубликаты, пропуски, подающий, победитель, переходы счёта и
  чередование подающего. Совместимые версии сверяются с числом геймов
  и счётчиками подачи. Пустые TB-счета и потенциально пропущенные последние
  очки ограничивают полноту. Исходный флаг сохраняется отдельно. Пропуск PBP
  не лишает подтверждённый результат пригодности для обновления состояния.
- **Прочий контекст.** Покрытие, поверхность, турнир, рейтинг и доступность
  проверяются отдельно. Коэффициенты изолированы для бэктеста.
  Рекомендации `popularMatches` и произвольный контекст страницы исключены.

Положительный статус качества характеризует саму проверку. Отдельный
`feature_eligible` учитывает время, идентификацию и конкретную группу.
`player_state_eligible` проверяет достоверный исторический результат
до cutoff. `model_baseline_label` проверяет пригодность метки для
прематчевого cutoff. Фактическое включение в датасет потребует отдельной
политики модели и проверки конкретного набора признаков.

## Версии и время

Версии объектов обособлены. Внутри объектов деталей, raw и статистики
разные `fetched_at` образуют разные наблюдения. Взаимная проверка возможна
по явной ссылке на совместимые версии или по единственному общему receipt
в деталях, raw и статистике, который записывает `detail_job.flush`.
Сравнение согласованности raw/details идёт внутри одной семьи источника.
Для PBP требуется явная связка версий. Неоднозначная совместимость выдаёт
`unverified`. Старый каталоговый аудит использует то же разбиение и тот же
критерий совместимости (Issue #88), а проверка качества новых данных
выполняется внутри ETL. Дата изменения объекта и положение в списке не определяют
выбранную версию.

`event_time` описывает событие, `available_at` — доказанный момент
доступности данной версии, `ingested_at` — получение источником,
`recorded_at` — доказанное время канонического решения, а
`prediction_cutoff` — момент допуска в расчёт. Для строки игрока и
алиаса на основании ревью используется отметка решения об идентичности.
Для остальных строк `recorded_at` берётся из `decision_at` данного
блока ревью. Без такого доказательства поле остаётся NULL.
Часы запуска используются только для публикации. При проверке
доступности учитываются известные верхние границы — дата решения и
время получения строки. Доказанное время доступности без обеих границ
сохраняется с ограничением допуска. Для строгого запуска
входы должны быть доступны раньше cutoff. Для postmatch-признаков
v1 дополнительно требует более ранний UTC-день. Рейтингу нужна дата
действия. При cutoff по умолчанию NULL строки сохраняются с закрытыми
временными воротами.

`historical_research_replay` публикуется в отдельном каталоге. Для
единственного валидированного наблюдения завершённого матча допускаются
последующие UTC-даты. Политика помечается как историческое допущение,
доказанное время сохраняется отдельно. Неоднозначные
исторические версии без подтверждённого выбора, рейтинги без даты
действия и коэффициенты остаются закрытыми. В режиме replay
наблюдения игроков могут быть предварительными, а проверенные
метки и допуск к обновлению состояния по-прежнему требуют
проверенного результата.

В конфигурации `reviews` индексируется по match_id. Каждый блок
привязан к точному `bundle_digest`, чтобы старое решение не применялось
к исправленным данным автоматически. Допустимые утверждения:

- Необязательное `decision_at` с UTC-offset — время принятия решения
  по этому блоку ревью. Если задано, датированные решения об идентичности
  и доказанная доступность источника должны укладываться в эту границу.
- `players["1"|"2"]` с `identity_key` (UUID), `evidence_ref` и
  `recorded_at` с UTC-offset.
- `tournament` с `edition_id`, `tournament_id`, `best_of`,
  `decider_rule` и `evidence_ref`.
- `compatible_versions` со списками `source_version`, которые явно
  связаны одним доказательством в проверенном блоке.
- `selected_versions[<источник>]` с `source_version`, `evidence_ref` и
  `recorded_at` для допуска одной версии из нескольких к заданному cutoff.
- `availability[<evidence_ref строки>]` с `available_at` и ссылкой
  на доказательство.
- `results[<evidence_ref строки>]` с `independent_winner_side`,
  выраженным в сторонах `matches`, и ссылкой на независимое доказательство.
  Это необязательное наблюдение. Противоречие блокирует определение победителя.
- `rankings[<evidence_ref строки>/p1|p2]` с `effective_at` и ссылкой
  на доказательство.

## Инкрементальная публикация и ограничения

ID снимка — SHA-256 канонического JSON манифеста без поля `version`.
Манифест фиксирует входы, конфигурацию, код и версии среды сериализации,
хеши итоговых Parquet-файлов и шардов, а также хеш сводки качества.
Одинаковые входы в одной среде дают побайтово одинаковые артефакты при
полной и инкрементальной сборке. При смене среды сериализации версия
может измениться. Время публикации, счётчики текущего запуска и список
инвалидаций хранятся вне версионируемых артефактов.

Изменение одного блока доказательств или одного манифеста пересчитывает
соответствующий матч. При повторном запуске ETL сверяет файлы без
повторного разбора неизменившихся строк. Итоговые таблицы собираются
потоково из проверенных шардов в порядке ID матчей. Временный каталог
и `CURRENT` публикуются атомарным rename на одном файловом разделе
под блокировкой писателя. Старый текстовый указатель читается при первом
запуске, прежние снимки сохраняются с их исходными ID.

Изменения и удаления инвалидируют старые и новые IDs обеих сторон.
Отчёт включает даты и самую раннюю затронутую дату. Состояния будущих
соперников могут зависеть от исправленного матча. В v1 ETL фиксирует
эту зависимость для последующего пересчёта, а движок состояния остаётся
следующим компонентом.

Размер обрабатываемых строк ограничен одним бандлом за раз. Индекс,
сводки и манифест хранятся в памяти, поэтому до подключения всей
истории потребуется дисковый индекс и секционированная публикация.
Измерение полного покрытия, поиск внешних доказательств, идентификация
редакций турниров, восстановление PBP и обучение модели не входят
в текущий импорт. Локальный ETL не обращается к production и сетевым
источникам.
