# Environment gotchas

Технические особенности окружения, которые не очевидны из кода и стоили реального debugging-времени.

## OOM при полном прогоне backfill_historical_pbp.py без фильтров

Полный прогон (все 64 группы `gender/level/year` в одном процессе, без `--only-*` фильтров) падал по нехватке памяти на машине с 4 ГБ RAM — трижды за один backfill, несмотря на переписывание `build_parquet_frame()` на колоночное накопление (список примитивов вместо `list[dict]`, снизило пиковую RSS с потенциально нескольких ГБ до ~500 МБ на самых крупных группах). Добавление 2 ГБ swap (было 1 ГБ) ослабляет риск, но не снимает его полностью: по `dmesg`/`journalctl` ни разу не было записи о kernel OOM-killer — убивал защитный супервизор харнесса Claude Code, следящий за доступной памятью извне процесса, а не сам Linux. Это значит, что даже щедрый swap не гарантирует защиты, если что-то снаружи процесса решает превентивно его остановить.

**Как обошли в этот раз**: запускали не один долгоживущий процесс на весь датасет, а отдельные `uv run ... --only-gender X --only-level Y --only-year Z` вызовы — по одной группе за раз, в foreground, с проверкой `free -h` между шагами. Идемпотентность скрипта (детерминированный `canonical_match_id`, проверка `existing_nbbet_ids`) сделала это безопасным — уже смигрированные группы просто быстро пропускались.

**Почему это важно для прод cron-скриптов** (`run_ingestion`/`run_features`/`run_inference`): их стоит с самого начала писать так, чтобы **один вызов обрабатывал одну единицу работы** (один день, один турнир) — а не крутил цикл по всему объёму данных в одном долгоживущем процессе. Иначе тот же сценарий (тихий, необъяснимый по логам ОС килл посреди прогона) повторится в проде без присмотра, и отследить причину будет так же тяжело, как в этот раз (никаких следов в `dmesg`/`journalctl`, только вывод "system is running low on memory" от внешнего супервизора).
