# Decisions

Журнал значимых решений по данным и модели — что исключили/включили и почему.

## Исключение exhibition-матчей и парного разряда из обучающих данных

Exhibition-матчи (EXHIBITION Мужчины/Женщины) исключены из бэкфилла: поочковые данные для них систематически неполны (60-62% матчей с оборванными/отсутствующими геймами против 1-4% у tour/challenger/ITF), плюс сама категория плохо репрезентирует соревновательную мотивацию игроков, на которой строится модель. Парный разряд исключён по объёму (около 25% всех собранных матчей) как находящийся вне скоупа проекта — модель ориентирована только на одиночный разряд ATP/WTA.

## Очистка дублей сырых бэкапов в S3 (2026-09-16)

В `s3://pelmen-data-storage/` обнаружено 13 копий исходных SQLite-баз (`tennis_matches.db`, `tennis_data.db`), раскиданных по `tennis_backups/` и корню бакета двумя волнами (июль и сентябрь 2026) без единой схемы именования. Оставлены только два полных несжатых снапшота, чей размер совпадает с текущими локальными базами (`tennis_backups/tennis_data.db`, `tennis_backups/tennis_matches.db`), остальные 11 удалены.

Схема для будущих raw-бэкапов: `raw_backups/{table}_{YYYYMMDD}.db.gz`, ретеншн на N последних версий — не класть в произвольный префикс.

## championat.com: обход SberID-редиректа через cookie unity_pause_sso

С 2026-09-16 `championat.com` отдаёт HTTP 200 с интерстишл-страницей "Авторизация SberID" на любой URL (проверено на страницах турнира, разделе тенниса, внутреннем API `/stat/data/live/tennis`, доменах `.com` и `.ru`) — сайт полностью закрыт для запросов без валидной сессии. Кука `unity_pause_sso=1` снимает этот редирект: с ней сервер отдаёт реальную страницу (`class="match-center-page tennis atp"` и весь контент) вместо заглушки авторизации. Проверено независимо 2026-09-20 (`curl -b "unity_pause_sso=1"`). Используется в `ingestion/http.py` как `CHAMPIONAT_COOKIES` для будущего championat-коллектора.

## nb-bet API: winner/server отсутствуют на уровне очка структурно, не из-за бага парсинга

Проверено на живом ответе `GET /v1/page-tennis-events-points/{id}` 2026-09-20: в объекте каждой точки (`points[]`) есть только `score_team1`, `score_team2`, `is_break_point`, `is_match_point` — ключей `winner`/`server` там нет вообще, ни пустых, ни нулевых. Дефолты `point.get('server', 0)`/`point.get('winner', '')` в старом `pbp_collector.py` — не потеря данных при парсинге, а корректная реакция на отсутствующий ключ: этих полей никогда не было в источнике на уровне очка.

На уровне гейма (`sets[].points`-родитель) реальные данные есть: `is_serve_team1`, `is_lost_serve`, `is_tiebreak`, `score_team1`/`score_team2` — то же самое, что `games_stats.server_team1` в исторической базе. Это подтверждает: реконструкция `point_winner` по прогрессии счёта + `server` из данных гейма (`ingestion/nbbet/pbp_parsing.py`) — единственный способ получить эти поля в принципе, а не обход испорченных данных. Важно для `nbbet/pbp.py` (инкрементальный коллектор поочковых данных, ещё не написан) — он должен реализовывать ту же реконструкцию, а не полагаться на поля `winner`/`server` из ответа API.

## nb-bet: статус матча есть, но не на уровне очка — на уровне листинга и страницы

Статус матча (SCHEDULED/LIVE/FINISHED/MOVED/CANCELED/STOPPED/INTERRUPTED/WALKOVER/FINISHED_RETIRED/AWARDED, enum 1–10 — см. `ingestion/nbbet/status.py`) присутствует и проверен в двух местах: в листинге `/v1/tennis/results/page` поле `"1"` каждого матча, на странице матча `__NEXT_DATA__ -> pageTennisEvent.match["23"]`. Значения совпадают (проверено на 20 завершённых матчах без расхождений, 2026-10-05). Поле `"1"` присутствует и в исторических листингах (проверено на дне 2019-06-15) — статус для всей истории можно получить без открытия страниц, обходом листинга по дням.

Числовой `nbbet_match_id` без текстового слага не работает ни на странице (`GET /tennis/events/{id}` → 404), ни в points API (`GET /v1/page-tennis-events-points/{id}` → 200, но с `errorCode:404` внутри тела и пустыми данными) — проверено 2026-10-05. Слаг обязателен, отсюда колонка `Match.nbbet_slug`.

## Текущий `pbp/` смещён в сторону равных матчей — не обучать модель до конца бэкфилла 111 тыс. матчей

Старый `pbp_collector.py` писал в `matches_main` только через `WHERE score1 > 0 AND score2 > 0` (подтверждено: в `matches_main` нет ни одной строки с нулём у кого-то из счёта, 0 из 110,263). Это значит, что весь текущий `pbp/` в S3/Postgres содержит только матчи, где обе стороны выиграли хотя бы один сет — то есть исключены все "сухие" 2:0/3:0 победы. Любой признак, построенный на очках (доля очков на подаче, частота брейков, длина геймов), систематически смещён в сторону близких/равных по уровню пар. До завершения прогона оставшихся ~111 тыс. matches-кандидатов (см. отчёт по объёму) **на этом наборе нельзя ни обучать, ни оценивать модель**.

## Счёт по сетам в листинге/матче не определяет завершённость — только статус

В `matches_main` (где `score1`/`score2` скопированы из `matches` без изменений) встречаются финальные счета 1:1 (1,598 строк) и 2:2 (20 строк) — таких исходов в теннисе не бывает у завершённого матча. Это снявшиеся/прерванные матчи: счёт на момент остановки, не финальный результат. Значит, признак завершённости матча — только статус (`FINISHED`/`FINISHED_RETIRED`/`AWARDED`, терминальные коды `status.TERMINAL`), а не сравнение score1/score2 между собой.

## Скоуп регулярного сбора nb-bet: tour и challenger, без ITF

`sweep.py`/`detail_job.py` по умолчанию берут `--levels tour,challenger`. ITF сознательно не трогаем: на живой странице матча блок «Статистика» (`match["25"]`) у ITF пуст на 30 из 30 проверенных матчей — покрытия там просто нет у источника, качать нечего. Уже загруженные ITF-строки (из исторического backfill) не трогаются и остаются как есть. Включить ITF в будущем — `--levels tour,challenger,itf`, без изменений в коде.

## detail_job: дубликаты в S3 допустимы, дедупликация — при чтении

Матч считается закрытым только после записи в S3 и обновления `Match` в Postgres одной транзакцией; если процесс падает между этими двумя шагами, в S3 может остаться файл без соответствующего обновления строки (или матч подхватится повторно следующим запуском). Явно не боремся с этим на уровне записи — имена файлов включают `run_id` (`part-{run_id}-{batch_idx}.parquet`, `run_id` монотонно растёт во времени), поэтому при дублях читатель должен дедуплицировать по ключу матча и брать файл с более поздним (большим) `run_id` в имени. Так уже предотвращён баг с перезатиранием `part-0000.parquet` из backfill свежими очками.

## Нераспознанные очки в detail_job: точный детектор, масштаб мал, алгоритм не меняем

Эта запись переписывалась трижды. Первые две версии опирались на широкий признак ("один счётчик не меняется 6+ очков подряд") и давали завышенную оценку масштаба (50% матчей) — он ловит и настоящий брак, и совершенно законный долгий deuce (один игрок раз за разом берёт и теряет advantage, из-за чего счёт соперника визуально "замирает" на `40`). Ниже — финальная версия с точным критерием.

**Точный критерий недопустимого состояния:** у одной стороны счёт `'A'`, а у другой — что угодно, кроме `'40'` (`15:A`, `0:A`, `A:30` и т.п. невозможны в теннисе; `40:A`/`A:40` — нормальный deuce).

**Проверено на 300 случайных матчах (2025-2026, tour+challenger, 5,618 обычных геймов без тай-брейков):**
- Недопустимых состояний: **0 геймов из 5,618, 0 матчей из 300.** Статистически это не противоречит истинной частоте около 0.6% матчей (как у явно нераспознанных очков) — при такой частоте ожидалось бы ~1-2 совпадения на 300, получить 0 — в пределах обычного разброса (не ноль по определению, просто выборке не попалось).
- Геймов с `game_complete=False`: 8 из 5,618 (0.14%) — ни один не содержит недопустимого состояния (другая причина, вероятно тот же буквальный повтор строки, что у тай-брейков).
- Матчей с законным долгим deuce (6+ очков, обе стороны в `{40,A}`, без недопустимых состояний): **192 из 300 (64%)** — это даже больше прежних "50%", что подтверждает: широкий скан в основном ловил законную игру, не брак.
- Для сравнения — 5 заведомо известных матчей с недопустимым состоянием (из прежней выборки, НЕ случайные): средняя `pbp_completeness` 0.9578, против 0.9983 у случайных 300 — недопустимые состояния действительно коррелируют с более низкой completeness, но размер этой группы (5) слишком мал для количественных выводов.

**Причина самого недопустимого состояния (откуда берётся `15:A` вместо `15:40→game`) по-прежнему не выяснена** — две гипотезы из предыдущей версии записи (нестандартное использование `'A'` источником vs потерянные обновления счёта соперника) остаются непроверенными, но при частоте <1% это не требует разрешения прямо сейчас.

**Решение:** `reconstruct_point_winner`/`is_game_complete` не меняем — подтверждённый масштаб (≤130 матчей из 21,700+, т.е. ~0.6%) не оправдывает сложность. При обучении модели достаточно фильтровать по `pbp_completeness` (порог решается отдельно), а не чинить алгоритм реконструкции. Тай-брейк — отдельный, уже задокументированный случай (буквальный повтор строки), не связан с этим критерием.

## nb-bet: листинг результатов по дню — не стабильная, догоняющая выборка

Запрос `/v1/tennis/results/page?timestamp=<день D>` систематически возвращает матчи с реальной датой старта **D-1** (проверено на двух независимых неделях — 215/215 и 316/316 совпадений смещения, без исключений), а не "матчи дня D" буквально. Хуже того: конкретный матч может первое время быть виден под "своей" корзиной (день D = его реальная дата), а через несколько часов переехать под корзину D+1 и пропасть из корзины D — наблюдалось напрямую (31 матч с реальной датой 2026-10-03 исчез из корзины 10-03 и появился в 10-04 в пределах ~2 часов). `Match.match_date`/`start_ts` считаются из реального таймстемпа поля `"4"`, а не из того, какую корзину мы запросили — поэтому сами данные не искажаются, но **однократный обход диапазона не гарантирует полноты за последние 1-2 дня**. Отсюда два sweep-а с перекрывающимися окнами: 3-часовой (`--start 3 days ago`) и суточный (`--start 14 days ago`) — подстраховка на случай более долгого дозаполнения. На старой истории (3 месяца 2+ лет назад) повторный sweep дал 0 новых строк — устойчивость подтверждена, догоняющий эффект актуален только для недавних дней.

## detail_job: правила остановки по 403/429

`ThrottleGuard` считает 403/429 среди последних 200 ответов; срабатывает при ≥3 плохих и доле >1% в окне. При срабатывании пауза между запросами удваивается, джоб засыпает на 300с и сбрасывает счётчик; после 3 срабатываний подряд — выход с кодом 2 (означает: сайт ограничил нас, cron просто перезапустит через 10 минут и упрётся в тот же лимит — see `docs/environment-gotchas.md`/README крона про `grep -c "слишком много 403/429"`). Статусы 429 выведены из автоматических ретраев `requests` (`make_session(retry_statuses=...)` без 429) специально, чтобы они доходили до `ThrottleGuard`, а не глотались транспортным слоем.

## Match.start_ts: UTC без tzinfo, не заменяет match_date

`start_ts` (реальный таймстемп старта, поле `"4"` листинга) хранится как naive-datetime в UTC — сервер и так в `Etc/UTC` (`timedatectl`, `time.tzname == ('UTC','UTC')`), но зависимость от tz сервера сознательно не закладываем: `discovery.py` считает его явно через `datetime.fromtimestamp(..., tz=UTC).replace(tzinfo=None)`, без обращения к локальной зоне. `match_date` продолжает считаться отдельно, тем же способом (`.date()` от того же timestamp) — `start_ts` не переопределяет и не перепривязывает `match_date`, это дополнительное, более точное поле для анализа по часу/дню. Расходов `start_ts::date <> match_date` на проверке не найдено (0 из 193 заполненных строк) — перепривязка `match_date` на `start_ts`, если понадобится, остаётся отдельным решением, не делается просто по факту появления нового поля.

## Правило выборки для обучения модели

`SELECT ... FROM matches WHERE status IN (3, 9, 10) AND duplicate_of IS NULL`. `status` отсекает незавершённые/отменённые/перенесённые матчи (см. запись про статус выше); `duplicate_of IS NULL` отсекает "лишнюю" сторону подтверждённых дублей (84 группы на 2026-10-06, из них 77 размечены как настоящие дубли через `pipeline/mark_duplicates.py` — идентичный `start_ts`, общий `pbp_s3_path` при наличии pbp у обеих строк; остальные 7 групп — не дубли, см. ниже). `pbp_completeness` в это правило не входит — это фильтр качества, применяемый отдельно при построении конкретных признаков (порог решается по задаче), не часть выборки "какие строки матчей существуют".

При чтении `pbp/` напрямую (без Postgres) нужно соединять по `Match` и тем же условиям — иначе дубль, у которого обе стороны имели `has_pbp=true`, даёт очки дважды. Проверено: ни у одной из 7 НЕ размеченных групп (2 вне окна ±2ч, 3 "переноса" с разным статусом/временем, 2 с status not in (3,9,10) у обеих/одной строки) `has_pbp=true` не стоит на стороне со статусом не 3/9/10 — риска утечки через не размеченные группы нет.

Отдельно: 51 пара на соседних датах (match_date различается на 1 день) — это НЕ дубли. На одном примере (634087/634540, Познань) подтверждено живым запросом: разные итоговые счета (3:6,4:6 против 6:1,6:3). 44 из них (оба статуса терминальные, Δstart_ts 24-31ч) разбросаны по 15+ разным обычным турнирам (не командные форматы) без концентрации — рабочая гипотеза: "lucky loser" пересдача (проигравший квалификации на следующий день попадает в основную сетку против того же соперника), не проверено на всех 44, только на одном.

## championat исключён из конвейера (решение владельца)

Основной фокус проекта — challenger-уровень, а у championat нет ни challenger, ни ITF (только tour). Дальше championat не переносим: ingestion-код под него не пишем, sqlite-база (`tennis_data.db`) и её копия в S3 (`tennis_backups/tennis_data.db`) остаются как архив — не удаляются, но и не обновляются. Не перенесено и не будет: рейтинги игроков (последняя неделя в архиве — 2026-06-15), турниры, призовые (`tournament_prizes`), `match_stats`.

Открытый вопрос снят следующей же проверкой (см. запись про рейтинг на nb-bet ниже) — championat как источник рейтингов не нужен.

## 44 пары на соседних днях — подтверждено не дубли, причина не выяснена

Дополнение к записи про `duplicate_of` выше: все 44 пары (один турнир, те же игроки, Δstart_ts 24-31ч, оба статуса терминальные) при точечной проверке дают разный итоговый счёт — это настоящие разные матчи, не ошибка данных нашей стороны. Почему те же два игрока официально встречаются дважды в одном одиночном турнире за сутки ("lucky loser" пересдача после квалификации — рабочая гипотеза, не подтверждена документально) — не выяснено. Группы не размечаются `duplicate_of`, обе строки участвуют в обучении как отдельные матчи.

## Рейтинг игроков берётся со страниц матчей nb-bet, не с championat

`match["3"]`/`match["5"]` (игрок 1/2) на странице матча содержат `{"1": имя, "2": фото, "3": bool, "4": {"1": ранг, "2": "ATP"/"WTA"}}`. Проверено на 6 матчах (tour/challenger/ITF, 2018-2026, включая 754772) — поле `"4"` есть везде, никаких `points` (очков рейтинга), возраста, роста или руки в этой структуре не найдено ни на одном уровне.

**Ранг — на дату матча, не текущий.** Джокович: ATP 7 на странице матча 2025-09-05, ATP 11 на странице матча 2026-10-05 — разные значения у одного игрока в зависимости от того, какую страницу открываем, не замороженное "текущее" число.

**Охват по годам** (15 challenger-матчей на год, статус 3, разные турниры, 2016/2018/2020/2022/2024/2026): 60%, 100%, 100%, 80%, 80%, 53%. Пропуски — **не брак**: во всех 19 случаях, когда ранг отсутствует у одной стороны, у другой он есть (оба `None` не встретились ни разу) — это безрейтинговые игроки (вне топ-N ATP/WTA, обычное дело на challenger-квалификации), а не дырка в данных источника.

**Еженедельное обновление подтверждено косвенно**: на 10 матчах Джоковича и 10 Алькараса (tour, 2025) подряд ранг не менялся внутри одной недели ни разу; единственное изменение у Джоковича (7→5) пришлось на промежуток 13 дней без промежуточного матча — не противоречит официальному еженедельному циклу ATP/WTA, но и не фиксирует точный день смены (нет пары матчей по разные стороны одного понедельника).

Открытый вопрос: очков рейтинга (ATP/WTA points, не позиция) на nb-bet нет вообще — если понадобятся, источник не определён (championat как архив не обновляется, см. запись выше).

Правило "новое поле не требует перекачки, т.к. есть сырой объект" **не работает для коэффициентов** — для них нужен снимок, сделанный рядом по времени с самим матчем (до его начала или сразу после), то есть именно механизм части B (сбор в sweep). **Правило про "новое поле не требует перекачки" остаётся верным для ВСЕХ полей, КРОМЕ коэффициентов** (ранг, статистика, сеты — подтверждено не деградируют со временем). ## odds_open: колонки Match, правило "один раз", источник записан как есть

5 колонок (`Match`, миграция `439ea87ea48e`): `odds_open_p1`/`odds_open_p2` (`NUMERIC(7,3)`), `odds_open_captured_at` (когда впервые увидели), `odds_open_source` (`'listing'` | `'page'`), `odds_open_status` (статус матча в момент захвата). Два `CHECK`: `ck_matches_odds_open_gt1` (обе цены > 1) и `ck_matches_odds_open_pair` (обе `NULL` либо обе не `NULL` одновременно) — оба в Postgres допускают "обе NULL" как тривиально проходящий случай (`NULL > 1` не `false`).

**Правило: пишется один раз, при первом наблюдении.** И `sweep` (источник `'listing'`, из `match_6` листинга — см. `odds.py:odds_pair`), и `detail_job` (запасной путь, источник `'page'`, из `match["30"]` страницы, срабатывает только если `sweep` не успел) делают `UPDATE`/`ON CONFLICT` строго с условием "текущее значение в БД ещё `NULL`" — повторные проходы с другой ценой её не перезаписывают. Это не "текущая" цена (она движется до начала матча) — это именно первая увиденная нами, поэтому `source`/`status`/`captured_at` относятся к тому же моменту, что и сами цифры. `sweep` дополнительно перед записью сверяет (допуск 0.0005) новую цену с уже сохранённой, если такая была — расхождение не блокирует запись (всё равно пишется один раз), но логируется с количеством и до 5 примеров, и уходит в `job_runs.error_sample`.

**Букмекер не определён.** В данных страницы/листинга нет текстового названия — только числовые id рынков внутри `match["30"]`/`match["31"]` (см. запись про A1-A4 выше). По оформлению интерфейса источника (не из данных, не проверено программно) похоже на LEON — это предположение, не факт, в колонках букмекер не хранится вообще.

Код: `ingestion/nbbet/odds.py` (`odds_pair`), `discovery.py` (`NbBetCandidate.odds_open`), `sweep.py` (`upsert_candidates`/`check_odds_consistency`), `detail_job.py` (`flush()`, запасной путь по `match["30"]`), `pipeline/backfill_open_odds.py` (разовый backfill из уже накопленного `nbbet_raw`, по умолчанию без записи).

Ручной прогон `sweep` за 3 дня (2 раза подряд): 141 строка с ценами, счётчик расхождений между прогонами = 0, новых строк во втором прогоне = 0 — идемпотентность подтверждена напрямую.

`backfill_open_odds.py` без записи (сканирование всего `nbbet_raw`, 1,700 файлов, 100,361 уникальных матчей по максимальному `fetched_at`): нашлось 1,545 строк, где цена в сыром объекте есть, а в Postgres `odds_open_p1` ещё `NULL` — все из 2026 года (challenger 1,142 + tour 403); 2022/2023 — 0 (согласуется с найденным ранее отсутствием коэффициентов на страницах того возраста). `--apply` не запускался — ждёт подтверждения числа 1,545.

## sweep: счётчики inserted/updated были неверно названы — исправлено

Обнаружено прямой проверкой: последний реальный запуск `nbbet-sweep` отчитался `inserted=318`, а фактически новых строк `matches` (по `created_at` в окне запуска) оказалось **0** — все 318 кандидатов уже существовали, upsert их просто обновил. Причина: `h.add(inserted=len(cands))` считал "сколько кандидатов обработали", а не "сколько строк создали". Отдельно `updated` использовался для числа снимков коэффициентов в S3 — вообще не про строки `Match`.

**Исправлено.** `upsert_candidates` теперь возвращает настоящие (вставлено, обновлено) через `RETURNING (xmax = 0)` — системная колонка Postgres: `0` у свежей `INSERT`-строки, не `0` у строки, прошедшей `ON CONFLICT DO UPDATE` (проверено отдельно в транзакции с `ROLLBACK`, см. изменения в `sweep.py`). Снимки коэффициентов больше не пишутся в `job_runs.updated` — только в лог. На тесте: тот же трёхдневный прогон дал `inserted=0, updated=167` — совпадает с фактом (0 новых строк, 167 уже существующих тронуты апдейтом).

## health.py: running-джоба с длинной сессией — свежесть по heartbeat, не по "давно не было ok"

`_check_schedule` сравнивал только момент последнего ЗАВЕРШЁННОГО (`status='ok'`) запуска с порогом `period * GRACE_FACTOR` — не видел вообще, что джоба `status='running'` прямо сейчас и исправно пишет heartbeat. ## Перекачка details_version<3: остаток, скорость, error_sample — не те же 3 матча

Остаток: challenger 13,721 + tour 10,970 = 24,691 строк с `details_version < 3`. Скорость (последние 3ч, строки, перешедшие в v3): 6,400 ≈ 2,133/ч — почти целиком `nbbet-refresh` (основная очередь пуста, новых матчей в час кратно меньше). Оценка до конца: **~11.6 часов (~0.5 суток)**.

`error_sample` у запусков `nbbet-refresh` с `errors_count=3` (несколько подряд: id 607/667/700/733) — везде `HTTPError('429 ...')` на РАЗНЫХ `nbbet_match_id` (618034, 644549, 671101, 696304, 747473 и т.п.), которые не совпадают ни с одним из 3 матчей из «отказов» (386716, 386714, 377838 — status=tour/challenger 2022, `details_attempts=5`). **Это не те же матчи.** `errors_count=3` — это сигнатура одного срабатывания `ThrottleGuard` (порог `min_bad=3`), после которого батч откатывается (`cursor = prev_cursor`) и повторяется — те самые 3 матча почти наверняка прошли на повторе и НЕ попали в постоянные отказы; 3 "отказа" — отдельные, не связанные матчи, упёршиеся в `details_attempts>=5` по другой причине (не 429, иначе откат спас бы их так же).

Проверено по всем 5 запускам `nbbet-refresh` с непустым `error_sample` за всю историю — **0 повторов** nbbet_match_id, каждый раз другой матч; подтверждает, что это обычный шум throttling, не застревание на конкретных матчах.

## 3 постоянных отказа (details_attempts=5) — не 429, а битый slug (404)

377838 (challenger), 386716/386714 (tour), все 2022 года. Причина — НЕ throttling: по логу (`nbbet_details.log`) все три с 2026-10-07 по 2026-10-08 систематически получали `страница 404`, при каждой из 5 попыток. `nbbet_slug` у всех трёх — `{id}--prognoz-na-match` (**двойной дефис**, имена игроков пустые) — slug собран без имён игроков ещё на этапе sweep/discovery (player1/player2 были пустыми строками в листинге на момент обнаружения этих матчей), и такой URL на сайте не резолвится. Это брак на стороне исходных данных конкретно этих 3 строк (пустые имена в листинге), а не ошибка детейл-джоба — ретраи были правильным поведением, после 5 попыток строки корректно выпали из очереди навсегда.

## odds_open: охват только 2025-2026, и почти весь захват — уже на завершённом матче

По году×уровню (processed tour/challenger): **0% до 2025 включительно** — 2016-2024 все строго 0, 2025 — 62.3% (challenger)/52.4% (tour), 2026 — 62.8%/64.0%. Источник: 2025 целиком `page` (запасной путь `detail_job`), 2026 — смесь `listing` (474 challenger + 278 tour) и `page` (остальное). `odds_open_status` (статус МАТЧА в момент первого наблюдения цены) среди всех 23,969 строк с ценой: status=1 (SCHEDULED) — 28, status=2 (LIVE) — 5, **status=3 (FINISHED) — 23,118**, status=9 (FINISHED_RETIRED) — 818. То есть **почти вся база "начальных" цен на самом деле захвачена уже на завершённом матче**, не до его начала — запасной путь срабатывает, когда `nbbet-refresh` впервые доходит до страницы, а это обычно случается уже после того, как матч закончился.

Из 782 `listing`-строк (цена увидена в листинге, а не на странице) — 40 на status=1, 6 на status=2, 688 на status=3, 16 на status=5 (CANCELED), 1 на status=8 (WALKOVER), 31 на status=9.

## Тест TennisExplorer как источника коэффициентов для challenger

**Запросов использовано: 11 из 40.** Пауза 3с, один поток, обычный UA, без обхода защиты.

**Шаг 0 (правила сайта).** `robots.txt` разрешает общий обход (блокирует только `/redirect/`, `/terms-of-use/`, `/contact/`) — страницы результатов/турниров НЕ в списке запрета. Но сама страница `/terms-of-use/` **явно в Disallow** — не запрашивал её (это и есть соблюдение правил, а не обход защиты), поэтому буквальный текст условий использования показать не могу. Открытый вопрос: формальное разрешение на автоматический сбор текстом не подтверждено, хотя сам `robots.txt` сбор результатов не блокирует.

**Шаг 1 (выбор матчей, Postgres).** A = ATP Challenger Poznań 2025 (2025-06-15..21, 49 матчей, 21 с `odds_open`); B = тот же турнир 2023 (2023-06-18..24, 49 матчей, 0 с `odds_open` — ожидаемо); C = ATP Challenger Villena 2026 (2026-10-04..09, 46 матчей, 37 с `odds_open`, 4 на `status=1`).

**Шаг 2 (структура сайта).** Один URL на турнир-сезон: `/{slug}-challenger/{year}/atp-men/` (главная сетка) + `/{slug}-challenger/{year}/atp-men/?phase=qualification` (квалификация) — слаг и структура найдены по реальным ссылкам на страницах (calendar → страница турнира → архив сезонов), не угаданы. Главная цена в таблице результатов (класс `best-betrate`) — ПОДТВЕРЖДЕНО со страницы деталей матча (`/match-detail/?id=...`), это строка **"Average odds"** (среднее по нескольким букмекерам из их сетки), не "лучшая цена одного букмекера" несмотря на название класса, и не явно обозначено как "closing" — но у отдельных букмекеров трек показывает движение до момента, близкого к началу матча (не строго open).

**Шаг 3 (покрытие).** По названию+дате+игрокам (с транслитерацией) сошлось 33/32/30 из 49/49/46; остаток почти целиком — совпадения по датам и точному счёту сетов, не найденные из-за транслитерации (пример: "Хорда Санчис"↔"Jorda Sanchis", "Алвеш"↔"Alves", "Пас"↔"Paz" — подтверждено сверкой счёта вручную). После сопоставления по (дата+счёт, с поправкой на формат тай-брейка "65"→"6") итоговое покрытие: **A 49/49 (100%), B 48/49 (98%), C 44/46 (96%)**. У всех сопоставленных матчей со статусом "показывает коэффициенты" на сайте — оба коэффициента есть (141 строка). Матчей на сайте, которых нет у нас в выборке, не считал отдельно (сайт даёт ровно main+qualification, у нас есть и то, и то).

**Шаг 4 (сверка цен).** 139 пар с надёжно установленным порядком игроков (по счёту сетов, не по транслитерации имени — первая попытка через транслитерацию дала ложное расхождение на паре Джере/Бартон из-за "дь"→"дж"). Доля побед фаворита по цене сайта (все 139 найденных матчей): **66.2% (92/139)** — в ожидаемом коридоре 62-72%.

Из них 55 пар, где есть и наш `odds_open`, и цена сайта:
- разница вероятностей без маржи (p_site − p_our): среднее 0.0010, медиана 0.0027 — близко к нулю в среднем;
- доля |разница|>0.03 — 36.4%, >0.05 — 20.0% — заметная доля отдельных случаев расходится сильно, даже при небольшом среднем смещении;
- доля совпадения фаворита: 94.5%;

### Выводы

1. **Разрешён ли сбор.** `robots.txt` не блокирует страницы результатов/турниров (блокирует только 3 административные страницы, включая саму страницу условий). Буквальный текст условий использования не прочитан (сам этот путь в Disallow) — формальное разрешение на автоматический сбор НЕ подтверждено текстом, только отсутствием блокировки в `robots.txt`.
2. **Покрытие по годам.** 2025 и недавний период (2026) — коэффициенты есть, сопоставление 96-100% после поправки на тай-брейк; 2023 — коэффициентов НЕТ вообще (0 турниров нашей выборки). Коэффициенты TennisExplorer на этом турнире обнаружены только начиная где-то между 2023 и 2025 — точная граница не определена этим тестом (отдельная задача, если нужна точность).
3. **Что за цены.** Явно подписаны на сайте как **"Average odds"** — усреднение по нескольким букмекерам, не "лучшая" и не однозначно "закрывающая". Соотношение с нашими: совпадение направления фаворита хорошее (94.5%), но точечное совпадение вероятности слабее (36% случаев расходятся на >0.03) — разные источники, разный момент снятия, ожидаемо не идентичны.
4. **Трудоёмкость на год challenger.** 1 турнир = 2 запроса (main+qualification). В 2023 было 228 уникальных турниров-строк challenger (не все уровня "турнир целиком", но порядок величины) → ≈400-460 запросов на весь год при паузе 3с ≈ 20-25 минут чистого времени запросов (без учёта разнесения по дням ради вежливости к серверу).
5. **Пригоден ли источник.** Структурно — да, экономичный метод (1-2 страницы на турнир, не по дням), числа разумные (доля фаворита в ожидаемом коридоре). Мешает: (а) не прочитан текст условий использования — юридический статус автосбора неясен; (б) цена — усреднённая, не прямое соответствие нашей "первой увиденной"; (в) охват по годам неизвестен за пределами 2023/2025/2026 (нужна отдельная проверка границы); (г) сопоставление матчей требует аккуратной транслитерации или сверки по счёту — простой name-matching не сработает "из коробки".
