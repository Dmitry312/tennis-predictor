# Decisions

Журнал значимых решений по данным и модели — что исключили/включили и почему.

## Исключение exhibition-матчей и парного разряда из обучающих данных

Exhibition-матчи (EXHIBITION Мужчины/Женщины) исключены из бэкфилла: поочковые данные для них систематически неполны (60-62% матчей с оборванными/отсутствующими геймами против 1-4% у tour/challenger/ITF), плюс сама категория плохо репрезентирует соревновательную мотивацию игроков, на которой строится модель. Парный разряд исключён по объёму (около 25% всех собранных матчей) как находящийся вне скоупа проекта — модель ориентирована только на одиночный разряд ATP/WTA.

## Очистка дублей сырых бэкапов в S3 (2026-09-16)

В `s3://pelmen-data-storage/` обнаружено 13 копий исходных SQLite-баз (`tennis_matches.db`, `tennis_data.db`), раскиданных по `tennis_backups/` и корню бакета двумя волнами (июль и сентябрь 2026) без единой схемы именования. Оставлены только два полных несжатых снапшота, чей размер совпадает с текущими локальными базами (`tennis_backups/tennis_data.db`, `tennis_backups/tennis_matches.db`), остальные 11 удалены.

Схема для будущих raw-бэкапов: `raw_backups/{table}_{YYYYMMDD}.db.gz`, ретеншн на N последних версий — не класть в произвольный префикс.

## championat.com: обход SberID-редиректа через cookie unity_pause_sso

С 2026-09-16 `championat.com` отдаёт HTTP 200 с интерстишл-страницей "Авторизация SberID" на любой URL (проверено на страницах турнира, разделе тенниса, внутреннем API `/stat/data/live/tennis`, доменах `.com` и `.ru`) — сайт полностью закрыт для запросов без валидной сессии. Кука `unity_pause_sso=1` снимает этот редирект: с ней сервер отдаёт реальную страницу (`class="match-center-page tennis atp"` и весь контент) вместо заглушки авторизации. Проверено независимо 2026-09-20 (`curl -b "unity_pause_sso=1"`). Используется в `ingestion/http.py` как `CHAMPIONAT_COOKIES` для будущего championat-коллектора.

## nb-bet API: winner/server отсутствуют на уровне очка структурно, не из-за бага парсинга

Проверено на живом ответе `GET /v1/page-tennis-events-points/{id}` 2026-09-20: в объекте каждой точки (`points[]`) есть только `score_team1`, `score_team2`, `is_break_point`, `is_match_point` — ключей `winner`/`server` там нет вообще, ни пустых, ни нулевых. Дефолты `point.get('server', 0)`/`point.get('winner', '')` в старом `pbp_collector.py` — не потеря данных при парсинге, а корректная реакция на отсутствующий ключ: этих полей никогда не было в источнике на уровне очка.

На уровне гейма (`sets[].points`-родитель) реальные данные есть: `is_serve_team1`, `is_lost_serve`, `is_tiebreak`, `score_team1`/`score_team2` — то же самое, что `games_stats.server_team1` в исторической базе. Это подтверждает: реконструкция `point_winner` по прогрессии счёта + `server` из данных гейма (`ingestion/nbbet/pbp_parsing.py`) — единственный способ получить эти поля в принципе, а не обход испорченных данных. Важно для `nbbet/pbp.py` (инкрементальный коллектор поочковых данных, ещё не написан) — он должен реализовывать ту же реконструкцию, а не полагаться на поля `winner`/`server` из ответа API.
