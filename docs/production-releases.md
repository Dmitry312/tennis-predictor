# Production: текущая архитектура и план релизов

Статус: этап 1, проектирование. База аудита: main
`db8195e49778ecb7d417838943be818e2d72eaba`. Сервер не обследован.
Документ не является разрешением на подключение или изменение production.

## Подтверждённая конфигурация

- `.github/workflows/deploy.yml`: push только в main → сборка Dockerfile →
  публикация `latest` → SSH → login GHCR → Compose pull → up только postgres.
  Нет обновления host-кода, venv, cron, миграций, проверки готовности или отката.
  Нет явного fail-fast удалённого скрипта и сериализации деплоев.
- `infra/docker/docker-compose.yml`: PostgreSQL 16-alpine, именованный volume
  pgdata, порт только 127.0.0.1:5432, restart unless-stopped. App описан, но
  workflow его не запускает; pull затрагивает и PostgreSQL.
- Dockerfile содержит код и venv, но не каталог миграций. CMD вызывает
  `pipeline.run_inference`: сейчас заглушка, завершающаяся после сообщения.
  `run_ingestion` и `run_features` также заглушки.
- `infra/cron/tennis-predictor.crontab` вызывает Python из host-venv в
  `/root/Tennis_pelmen_model`, а не Docker: detail и refresh каждые 10 минут,
  sweep в минуту 15 каждые 3 часа, wide sweep ежедневно в 03:00,
  health check каждые 15 минут и summary в 08:00. Часовой пояс сервера неизвестен.
  Есть flock: sweep и wide используют общий lock, остальные — отдельные.
  Это шаблон в Git, установка и фактические команды на сервере не подтверждены.
- По подтверждению владельца SSH diagnostic от 4 ноября выполнил whoami.
  Повтор базовой диагностики не нужен. Host fingerprint пока не закреплён.
- Документация migration-status — историческое свидетельство, не актуальная
  инвентаризация. Незакоммиченный код и дополнительные зависимости надо проверить.

## Целевая структура

ROOT выбирается после инвентаризации: это не утверждение о наличии /opt.

```text
ROOT/
  releases/COMMIT_SHA/       # неизменяемый код и собственная .venv
  current -> releases/SHA
  previous -> releases/PREVIOUS_SHA
  shared/.env               # вне Git; ограниченные права
  bin/run-job               # стабильный launcher для cron
```

Релиз устанавливается сразу по окончательному пути, зависимости из uv.lock;
venv после установки не переносится. Артефакт и SHA проверяются до активации.
Путь shared/.env передаётся явно будущим launcher: существующая загрузка .env
из рабочего каталога сама не начнёт читать shared. Секреты не попадают в образ,
репозиторий, журналы и отчёт. В stage 1 launcher не реализуется.

Launcher сохраняет существующие имена, режимы ожидания и пути flock, nice,
аргументы, расписание и логи. Под блокировкой запуска один раз разрешает current
в физический путь, делает cd в этот релиз и exec его Python. Нельзя оставлять
ссылку current в путях импортов или поздних обращений к коду. Код не обновляется
на месте. Новый current публикуется атомарным rename подготовленного symlink
в том же каталоге/файловой системе. Деплои сериализуются, previous фиксируется
до переключения; состояние восстанавливаемо после сбоя между этими действиями.

Работающие задачи продолжают использовать старый релиз; новые получают новый.
Удалять старые релизы нельзя до подтверждения отсутствия использующих их задач
и окончания окна отката. Две версии могут одновременно писать в БД и S3:
нужны совместимые схемы и форматы. При несовместимости требуется отдельно
согласованная остановка новых запусков и ожидание завершения текущих.
Первичный переход старого cron делается после дренирования старых задач,
с сохранением прежнего запуска для отката; принудительная остановка не входит.

## Проверки и PostgreSQL

До активации: CI-тесты, установка из lock в изолированном окружении, тесты
launcher (фиксация релиза, flock, ошибки и переключение), проверка артефакта.
Интеграционные тесты только на отдельной тестовой БД без production-секретов.
Не импортировать приложение на production для smoke-test без анализа побочных
эффектов. Health check пишет job_runs и локальные файлы — не read-only.

Релиз приложения не делает compose pull/up/restart для PostgreSQL, не меняет
volume, credentials и схему. Первый переход — без миграций. Отдельно проверить
наличие и восстановимость backup; восстановление тестируется в изоляции.
Будущие миграции требуют отдельного решения и обратной совместимости.

После активации наблюдать обычные cron-запуски, коды завершения и SHA.
Для каждой задачи определить срок успешного запуска, допустимые задержки и
ответственного за остановку rollout. Отсутствие записи job_runs само по себе
не доказывает отсутствие процесса: трекинг допускает ошибки записи в БД.

## План отката

1. До любых изменений сохранить проверенный старый запуск cron, SHA, версии
   зависимостей и пути без копирования секретов в отчёт; определить владельца.
2. Неудачная подготовка релиза не меняет current: продолжает работать старый.
3. После неуспешной активации атомарно вернуть current на проверенный предыдущий
   релиз; новые задачи используют его. Запущенные задачи не прерывать.
4. На первом переходе вернуть согласованную прежнюю конфигурацию cron, если
   проблема в launcher; не запускать дубли и сохранить прежние flock.
5. Откат кода не отменяет записи БД/S3. Не выполнять автоматический downgrade
   схемы, восстановление БД или остановку задач. При несовместимости остановить
   rollout и согласовать отдельную процедуру.

## Условия перехода и небольшие PR

Этап 1 завершается ревью этих документов. До следующего этапа: отдельно разрешить
инвентаризацию, установить доверие к host key, подтвердить реальный путь, cron,
локальные изменения, Python/зависимости, процессы, locks, volume и backup.
При неизвестных данных или ошибках чтения отмечать UNKNOWN, не подбирать пути
и не устанавливать инструменты. Отсутствие доступа не означает отсутствие задач.

Порядок последующих PR (не выполняются этим PR):
1. Защита workflow: исключение непреднамеренного автодеплоя, fingerprint,
   pin actions на commit SHA, fail-fast, таймауты и concurrency.
2. Launcher с тестами и явной загрузкой окружения, без установки на сервер.
3. Подготовка проверяемого релиза без активации и без операций с PostgreSQL.
4. Отдельно согласованный первый переход cron и активация/откат.
5. Оповещения, журнал версий и осторожная очистка неиспользуемых релизов.

Важный барьер: нынешний workflow запускается при ЛЮБОМ push в main, в том числе
после merge документации. Не сливать этот PR до согласования защиты workflow.
Draft PR сам по текущему workflow деплой не запускает.

## SSH host fingerprint

Доверенный ключ/fingerprint получить через консоль провайдера или администратора
по независимому каналу. ssh-keyscan сам подлинность не подтверждает. Зафиксировать
проверенный SHA256 fingerprint в защищённой конфигурации GitHub Environment;
целостность важнее секретности. В будущем настроить fingerprint ssh-action,
сам action закрепить commit SHA. Несовпадение должно завершать workflow до
удалённых команд. Не отключать проверку и не принимать новый ключ автоматически.
Ротация — повторная независимая проверка. Проверка SSH не разрешает деплой.
